# Muse 编排纪律

## 三种形态并存，按确定性需求选择

| 形态 | 何时使用 | DSH 工具 |
|---|---|---|
| Workflow | 确定性要求高、步骤固定、首尾相接 | `workflow` 工具（代码编排，子调用结构化返回） |
| Pipeline | 需要按输入分流、对关键环节做局部控制 | workflow + 条件分支；关键节点人工确认 |
| Agent Team | 子任务**确实独立、可并行、上下文可分离、可独立验收** | `subagent`（后台并行）+ 汇总验证 |

## Agent Team 的硬约束

多 Agent 只在有真实收益时使用。出现以下任一情况，退回 Pipeline：

- 几个子代理需要**竞争写同一份可变资源**（同一文件、同一分支、同一条记录）
- 整条推理必须**严格串行**（后一步依赖前一步的判断）
- 子任务无法独立验收（边界模糊 = 重复工作和冲突的来源）

## 执行规范

1. **ownership 先行**：分派前写明每个子代理独占的产出（文件/模块/工件），禁止重叠写入。
2. **每个子任务一个 WorkUnit 视角**：子任务目标不可变、可独立验收；父任务用 `workunit` 跟踪整体。
3. **汇总必须验证**：合并子代理结论时检查矛盾（同事实不同结论 = 冲突，必须解决而非拼接）。
4. **过程指标**：完成后在 `workunit` 的 note 或 `eval_report` 前记录——重复工作（两个子代理做了同一件事）、冲突次数、汇总失败次数。这些和成功率一样是指标。
5. **副作用归父**：子代理只做只读分析或可回滚的草稿；写操作、外部动作由父代理统一经 effect ledger 执行（子代理无审批权）。

## 反模式

- 为了"显得并行"而拆分子代理
- 把汇总理解为拼接（矛盾结论拼在一起 = 汇总失败）
- 让子代理直接执行外部副作用
